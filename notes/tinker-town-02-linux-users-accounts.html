Admin users & service accounts

Created a dedicated sudo admin account (adm-fkar) instead of using the default ubuntu user, then built a proper no-login service account (svc-disk-report) to run background scripts under least privilege.

This establishes the identity model the rest of the lab's services build on.

Full command sequence

RemoteCreate the personal admin account

sudo adduser adm-fkar             # create user + home directory
sudo usermod -aG sudo adm-fkar    # -aG: append to the sudo group (keeps others)
groups adm-fkar                   # verify group membership

RemoteCopy the SSH key to the new user

sudo mkdir -p /home/adm-fkar/.ssh                                     # -p: no error if it exists
sudo cp ~/.ssh/authorized_keys /home/adm-fkar/.ssh/authorized_keys    # copy the allowed public key
sudo chown -R adm-fkar:adm-fkar /home/adm-fkar/.ssh                   # -R: hand folder to the user
sudo chmod 700 /home/adm-fkar/.ssh                                    # 700: only owner can enter
sudo chmod 600 /home/adm-fkar/.ssh/authorized_keys                    # 600: owner read/write only
Gotcha · SSH silently refuses keys if the .ssh folder or authorized_keys is owned by root or too open — the chown and chmod steps are what make the login work.

RemoteDelete a user (if starting over)

sudo deluser --remove-home fkar    # --remove-home: delete user + home dir

RemoteInspect users & groups

grep adm-fkar /etc/passwd    # user's UID / primary GID / shell
grep adm-fkar /etc/group     # group memberships
id adm-fkar                  # numeric UID/GID + all groups, human-readable
Tidier form · The original used cat /etc/passwd | grep adm-fkar. grep can read the file itself, so the cat and pipe aren't needed — same result.

RemoteCreate a service account

sudo useradd -r -s /usr/sbin/nologin svc-disk-report    # -r: system acct, -s: no-login shell

How Linux stores accounts

Concept/etc/passwd format

username:x:UID:GID:comment:homedir:shell

The 4th field (GID) points to the user's primary group — the one auto-created by adduser with the same name as the user.

Concept/etc/group format

groupname:x:GID:member1,member2,...

The member list only holds additional members (added via usermod -aG) — not the user whose primary group this is.

Where things live

WhatPath
User accounts/etc/passwd
Group definitions/etc/group
New user's authorized keys/home/<user>/.ssh/authorized_keys
Service account shell (blocks login)/usr/sbin/nologin

Best practices

Leave the default user behindDon't work as the provider's default user (ubuntu) long-term — create your own admin account.
Humans and services apartPersonal sudo accounts are for you; background services get their own dedicated accounts.
Service accounts are locked downNo login shell, no sudo, no password — least privilege by design.
One account per serviceContains the blast radius and gives a clearer audit trail.
Follow the naming ruleadm-<name> for personal admin, svc-<purpose> for services.
Build, then hand overBuild and test as your own account first, then give ownership to the service account once it works.
