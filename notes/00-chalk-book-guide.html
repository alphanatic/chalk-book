Chalk Book Guide

Purpose, structure & conventions

A personal technical chalk book. After a session of problem-solving, building or learning with an AI, the work is distilled into one calm, skimmable note that can be revisited later for a fast refresher, on a small local site or as a PDF.

This is the read-only copy of CLAUDE.md, which is the source of truth.

Local — your machine Remote — the server Config file Concept AWS Console Gotcha Best practice Paths

Purpose

  • Capture recent work while it is fresh: commands, configs, decisions, mistakes.
  • Revisit it later and get the gist in under a minute.
  • Repeat it cold, months later, without re-researching anything.
  • Trace what was done, per project and date, so a future AI can recall which scenarios have been worked through.

Two kinds of knowledge

Recurring

Used again and again: systemctl, ssh config, naming rules.

The note is a fast reference. Patterns, quick tables, the one flag you always forget.

One-off

Set up once, or a rare fix: growing an EBS volume, a logrotate permission error.

The note is a complete recipe. Every step in order, every flag explained, so it can be redone from zero.

Best practice · When in doubt, write for the forgetful future self. Assume nothing is remembered.

Anatomy of a note

Every note follows the same top-to-bottom shape, so the eye always knows where to look.

  • Header band: eyebrow chip PROJECT TINKER TOWN · 03 · MODULE 1 · 2026-08-30, title words coloured blue, pink, green, yellow in turn, a short subtitle, and a 1–2 sentence past-tense summary.
  • Legend: colour chips for every block type used in the note.
  • What we covered: a ✓ checklist of outcomes, skimmable on its own.
  • Full command sequence: steps under short headings, each tagged Local or Remote
  • Supporting sections: concepts, diagrams, field tables, quick-reference tables.
  • Bugs hit & fixed: one card per real error, Cause → Fix.
  • Where things live and Best practices (short cards) as needed.
  • Part of line: the project, with links to related notes through the site.
  • Footer on printed pages: Tinker Town 03 — Systemd Service · 1 / 3

Writing style

  • Skim first. Headings, checklists and tables carry the story; prose only fills gaps.
  • Short. Sentences under ~20 words. No intro paragraphs, no filler.
  • Every command gets a comment explaining what it does and what each flag means.
  • Config files stay clean. Annotations sit beside the file or in a field table, never inside it.
  • Real by default, except access, location and private life. Actual commands, paths and error messages, but: no keys, passwords or tokens; placeholders such as <instance-ip> for public IPs, account IDs and emails; nothing about the user's private life. Anything that looks like an admin account is always adm-kiwi: never a name, never a placeholder, live or test.
  • Keep the mistakes. Errors and their fixes are often the most valuable part.
  • Respect history. When a convention changes, mark old names as legacy instead of rewriting earlier notes.
  • Calm tone. Plain, friendly and factual. No hype, no emoji.
sudo mkdir -p /mnt/data    # -p: create parents, no error if it exists
Gotcha · Many config formats break on inline comments. That is why config blocks are never annotated inside the block itself.

Visual style

Key rule · chalk-pastel.css is the palette for every note, until the user says otherwise. Colours are used only through its variables, never as hex values. The file belongs to the user.

Concept · Notes link the palette instead of copying it. Changing chalk-pastel.css restyles every note at its next render; PDFs keep their look until re-rendered.

Layout lives in notes/note-layout.css: A4 on --paper, an --asphalt header band, Inter (bundled) for text, DejaVu Sans Mono (from the system, falls back to any monospace) for code, soft tinted blocks.

The site

  • index.html opens straight from disk, no build step. How it looks and behaves is in the code and in meta-01-site-build.
  • Site colours live in site/site-theme.css, never in the note palette. The name is always the shared <chalk-wordmark>.
  • After adding or changing a note, rebuild the search index: node site/build-index.mjs.
  • A new site page goes in site/pages/, then into PAGES in site/app.js and the main footer. New Export options are items in the Export menu.
  • Backlog and Complete Tasks are private pages in .prog/, gitignored, about Chalk Book itself only. A finished item moves to Complete Tasks only when the user asks, unchanged except a Done chip and a date.

How notes are made & changed

Concept · The notes are read-only by design. Nobody edits a note in a viewer; every change goes through an AI session.

Adding a note: the memory-dump skill

  • Work on something, in any project folder.
  • While it is fresh, say “memory-dump” or “chalk that up”. A personal pointer skill makes this work in every folder. An AI may also offer a dump when the topic changes or about an hour of content has built up.
  • The skill plans the notes, fills the template in notes/, adds them to site/notes.js, rebuilds the search index, runs check.sh and checks every page, then hands over following the user's own git preferences.
  • Check the note on the site and ask for any changes in the same session.

Changing a note or this guide

  • Ask for the change in a session. The AI edits the HTML source or CLAUDE.md.
  • Note PDFs are made on demand from the site; the originals from before the HTML rebuild and the last guide PDF are kept in archive/.

Rules for AI assistants

  • Read CLAUDE.md before creating or changing anything in the chalk book.
  • Use the memory-dump skill to make notes, and chalk-pastel.css for every colour.
  • Match the existing notes' structure and look exactly; open one as a reference if unsure.
  • Never edit, rename or delete an existing note or archived PDF unless the user asks.
  • Keep CLAUDE.md and this guide's HTML in sync, and change them only when the user asks.
  • Keep private data out before it is committed: GitHub may still serve a pushed commit after a force-push. If something slips through, tell the user; don't rewrite history without asking.
  • Git follows the person. Committing, pushing and commit-message style come from the current user's own instructions, never from this guide. If none are given, ask before any git action.
  • Git wording. Use git's own terms exactly: stage, commit, push, pull, revert, reset. If a request doesn't map clearly to one git action, ask, offering 1–3 options with a short description each.
  • Commit messages document the work: a title, then a body saying what changed and why.
