# Chalk Book — Project Guide

> A personal technical chalk book. After a session of problem-solving, building or
> learning with an AI, the work is distilled into one calm, skimmable note that
> can be revisited later for a fast refresher, on a small local site or as a PDF.

This file is the source of truth for how the chalk book works. It is written for any
future AI assistant or person picking up the project. A human-friendly copy is the guide
note, `notes/00-chalk-book-guide.html`.

---

## 1. Purpose

- **Capture** recent work while it is fresh — commands, configs, decisions, mistakes.
- **Revisit** it later and get the gist in under a minute.
- **Repeat** it cold, months later, without re-researching anything.
- **Trace** what was done, per project and date, so a future AI can skim the collection and
  recall which scenarios have been worked through.

### Two kinds of knowledge

Every note serves one or both of these readers:

| Kind | What it looks like | What the note must do |
|---|---|---|
| **Recurring** | Things used again and again (e.g. `systemctl`, `ssh` config, naming rules) | Be a fast *reference* — patterns, quick tables, the one flag you forget |
| **One-off** | Setup done once, or a rare fix (e.g. growing an EBS volume, a logrotate permission error) | Be a complete *recipe* — every step, in order, with every flag explained, so it can be redone from zero |

When in doubt, write for the forgetful future self: assume nothing is remembered.

### File naming

```
<project>-<NN>-<topic>.html
```

- `project` is the slug from the project list below, so the name says where the work happened.
- `NN` is two digits and counts up within each project, so `10` sorts after `09`.
- `topic` is 2–4 words naming the subject, not the outcome: `cron-logrotate`, not `fixed-my-logs`.
- Everything is lowercase kebab-case. One topic per file; a long session becomes several notes.
- The date, title, number and module live only in the catalogue (`site/notes.js`, or `site/notes-local.js` for
  private and pending notes); the note's header and footer are made from it.
- `00-` with no project is reserved for meta files about the chalk book itself. `<project>-00-` is that project's
  cover note, e.g. `pokedex-00-pokeggdex-at-a-glance`.

### Projects

| Slug | Display name | What it is |
|---|---|---|
| `tinker-town` | Project Tinker Town | Self-paced AWS Linux sysadmin lab, a one-week crash course in 7 modules |
| `pokedex` | Pokédex | The Pokédex web project |
| `claude-code` | Claude Code | Setting up and securing Claude Code itself |
| `javascript` | JavaScript | Learning JavaScript by reviewing and fixing a React todo app |
| `arch-linux` | Arch Linux | Installing and setting up Arch Linux on personal machines |
| `anthropic` | Anthropic | The claude.ai account: cloud skills, sync, and what reaches the local tools |
| `meta` | Chalk Book | Notes about the chalk book itself |
| `lkgexp` | *(private)* | A work course; its name and roadmap live only in `site/notes-local.js` |

Add a row before using a new project, and the same project to `CHALK_PROJECTS` in `site/notes.js`.
A project can carry a roadmap of modules there; the site shows unfinished modules as planned.

**Arch Linux and `lkgexp` are private.** Their notes and everything made from them are gitignored, never committed:
the notes (`notes/arch-linux-*`, `notes/lkgexp-*`), their catalogue entries (`site/notes-local.js`, not
`site/notes.js`) and their search text (`site/search-local.js`, written by `build-index.mjs`). `lkgexp` is defined
in `site/notes-local.js` too, roadmap included, so its name never reaches the repo. Each private note loads
`../site/notes-local.js` after `../site/notes.js`. `check.sh` fails if a private note's entry lands in `site/notes.js`.

**Every new note starts pending:** public or private is not decided yet. Its entry goes in `site/notes-local.js` with
`pending: true`, and the site shows it with a yellow Git mark. Its text stays out of `search-index.js`. `check.sh`
fails if a pending entry is in `site/notes.js` or a pending note is staged. When the user decides:

- **Public:** move the entry to `site/notes.js` without `pending`; the note can then be committed.
- **Private:** drop `pending`, keep the entry in `site/notes-local.js`, and add the note to `.gitignore`.

Arch Linux and `lkgexp` notes are private from the start, never pending.

### Note types

- **Walkthrough** — what was done in a session, start to finish. Most notes.
- **Reference** — a cross-cutting rulebook that other notes depend on
  (e.g. `tinker-town-05-naming-conventions`). Says so in its summary: *"a reference, not a walkthrough"*.

## 3. Anatomy of a note

Every note follows the same top-to-bottom shape, so the eye always knows where to look.

1. **Header band** (dark)
   - Eyebrow chip: `PROJECT TINKER TOWN · 03 · MODULE 1 · 2026-08-30` (project · number · module or `context`, if any · date)
   - Title, its words coloured in turn after the yellow chip: blue → pink → green → yellow
     (done by `notes/note.js`); every `&` is purple chalk (`--lav`), other symbols stay white
   - Subtitle: a short descriptive phrase
   - Summary: 1–2 sentences, past tense — what was built and why it matters to later notes
2. **What we covered** — checklist of ✓ outcomes, one line each, complete enough to stand in for the note
3. **Full command sequence** — the steps, grouped under short headings, each tagged
   `Local` or `Remote`
4. **Supporting sections** as needed — concepts, diagrams, field tables, quick-reference tables
5. **Bugs hit & fixed** — one card per real error: **Cause** → **Fix**
6. **Where things live** and **Best practices** (short cards) as needed
7. **Part of** line — the project, with links to related notes through the site
8. **Footer** (printed pages) — `Tinker Town 03 — Systemd Service · 1 / 3`

Notes are written in **chalk markup**: compact text that `notes/note.js` turns into this shape in the browser, with
no build step. The syntax is in the comment at the top of `note.js`, and `template.html` shows every part. The header and
footer are made for you; notes have no legend, since each block's tag and label already say what it is. Anything the markup can't say goes in a ```` ```html ```` block, unchanged.
The standard headings get ids on the page: `covered`, `steps`, `bugs`, `paths`, `practices`.

### Block types and colours

Local `--sky` · Remote `--lav` · Config file `--butter` (path as title) · Concept `--peri` · Gotcha `--peach`
(also bug cards) · Best practice `--mint` · Paths `--pink` · AWS Console `--coral`. What each is for is in the
comments of `chalk-pastel.css`.

Inline callouts use a bold label and a dot: **Gotcha ·**, **Concept ·**, **Key rule ·**, **Naming note ·**, **Updated rule ·**.

## 4. Writing style

- **Skim first.** Headings, checklists and tables carry the story; prose fills gaps only.
- **Short.** Sentences under ~20 words. No intro paragraphs, no filler.
- **Every command gets a comment** explaining what it does and what each flag means:
  `sudo mkdir -p /mnt/data   # -p: create parents, no error if it exists`
- **Config files stay clean.** Never put comments inside a config block (many formats
  break on inline comments). Annotations sit in a column beside the file, or in a field table below it.
- **Real by default, except access, location and private life.** Use the actual commands, paths and error messages
  from the session, with three exceptions:
  - **Access:** never write anything that grants access (keys, passwords, tokens, recovery codes), not even partly masked.
  - **Location:** anything that locates or identifies a host or account (public IPs, AWS account IDs, resource IDs,
    emails, internet hostnames) becomes a placeholder, `<what-it-is>` in lowercase kebab-case. Reuse an existing name
    where one fits: `<instance-ip>`, `<my-ip>`, `<vpc-id>`. Private ranges (`10.0.0.0/16`) and `0.0.0.0/0` are fine.
  - **Private life:** nothing about the user's life outside the work: home address, job search, health, other people.
    When in doubt, leave it out and ask.
  - **Names:** `critonite` and `kiwi` are the original author's aliases (`crit`, short for `critonite`, in hostnames).
    They may appear in that author's notes and commits (from 2026-10-18), and belong to no one else. Any other name of
    a person (real name, initials, another username) becomes a made-up cartoony or fruity one, like `mango` or `noodle`,
    never `kiwi`. One person keeps the same stand-in everywhere.
  - **Your alias:** each person writes under their own alias, kept in `~/.config/chalk-book/alias` (one word, never
    committed). It pairs with "Before your first note" in the README:
    - *For humans:* pick a nickname for privacy, or use your real name if you prefer.
    - *For AI:* at the first session in a clone, if that file is missing, look for an alias in the user's own
      instructions (global `CLAUDE.md` or memory). If there is none, ask the user to choose a nickname, or their real
      name if their preferences say so. Save it to the file. Never give anyone `critonite` or `kiwi`.
  - **Admin accounts:** anything that looks like an admin account (`adm-…`, `admin-…`, `…-admin`) is always written as
    `adm-<alias>`, never a real name and never a placeholder. This applies to live and test environments,
    patterns and examples alike. Commands stay exactly as run, with `adm-<alias>` in place of the name. Notes don't explain the
    substitution. The "Respect history" rule doesn't apply here: old admin names are never shown, not even struck through.
    The original author's notes use `adm-kiwi`.
- **Keep the mistakes.** Errors and their fixes are often the most valuable part. Record them as Bug cards.
- **Trim output.** Keep the few lines of output or log that matter, never the whole dump.
- **Respect history.** When a convention changes, update the reference note and mark old
  names as legacy (struck through, with a *Naming note*), rather than rewriting earlier notes.
- **Calm tone.** Plain, friendly and factual. No hype, no emoji.

## 5. Visual style

Soft, warm and easy on the eyes. Pastels only, no harsh borders, generous white space.

### Stylesheet rule

**`chalk-pastel.css` is the palette for every note, until the user says otherwise.**

- Every note loads it through `note.js`, before `note-layout.css` and the note's own `<style>`, if any.
- Colours are used only through its variables, e.g. `var(--lav-bg)`. No hard-coded hex values
  in notes or in `note-layout.css`.
- Each colour comes in four parts: the chalk colour for chips and borders, `-bg` for box tints,
  `-ink` for coloured text, `-chip` for text on a chip. The comments in the file say what each is for.
- The file belongs to the user. Do not edit it unless asked.
- Changing the palette restyles every note at its next render. PDFs keep the old look until re-rendered.

### Layout

Structure and components live in `notes/note-layout.css`, shared by every note: A4 portrait on `--paper`;
Inter, bundled in `notes/fonts/`, for text; DejaVu Sans Mono for code, from the system (falls back to any
monospace). Blocks and callouts use their colour's `-bg` tint.

### The site

`index.html` is a static site with no build step: it opens straight from disk. How it looks and behaves is
in the code and in `meta-01-site-build`.

- Site colours live in `site/site-theme.css`, never in `chalk-pastel.css`.
- The name is always the shared `<chalk-wordmark>` element.
- After adding or changing a note, rebuild the search index: `node site/build-index.mjs`.
- **Sets are lists.** Any set of buttons or labels in order (footer links, Export options, legend chips, table columns)
  is one ordered list in the script, which makes one element per entry. The page holds only an empty container.
- Add a site page: create it in `site/pages/`, then add it to `PAGES` and `FOOTER` in `site/app.js`.
- **Git marks** use three colours, everywhere: green = on GitHub, yellow = pending, red = private. Home shows one
  mark of each with its count (`HOME_MARKS`).
- **Menu sort** (`SORTS`): A–Ö, 01–99, Ö–A, lit yellow, green and red. Those colours are the user's choice and have
  nothing to do with the Git marks. 01–99 is the default.
- **Private footer links** (`private: true` in `FOOTER`) are the owner's own shortcuts: claude.ai, benchlm.ai, AWS.
  Like the private pages below, they show only where `.progress/backlog.html` exists.
- New Export options are entries in `EXPORTS` in `site/app.js`.
- **Backlog** (`#backlog`) and **Complete Tasks** (`#complete`) are private: `.progress/backlog.html` and
  `.progress/complete-tasks.html`, gitignored, never on GitHub or a hosted copy. They cover Chalk Book itself only;
  work inside a menu project belongs in its roadmap in `site/notes.js`. One exception: **Linux** (`#linux`),
  `.progress/linux.html`, is the user's own backlog for their Linux machines, private the same way, with its done
  items kept at its bottom. The folder was `.prog/` until 2026-10-18;
  older notes keep that name.

## 6. How notes are made and changed

The notes are **read-only by design**: nobody edits a note in a viewer. Every change
goes through an AI session.

**Adding a note: the memory-dump skill**

1. Work on something, in any project folder.
2. While it is fresh, say **"memory-dump"**, "chalk that up" or similar. A personal pointer skill in
   `~/.claude/skills/memory-dump/` makes this work in every folder and leads back to this project.
   An AI may also offer a dump; when is each user's own preference.
3. The skill plans the note(s), copies `template.html` into `notes/`, fills it in following this
   guide, adds it as pending to `site/notes-local.js` (§2), rebuilds the search index, checks every page, then hands over
   following the user's own git preferences (§7).
4. Check the note on the site; ask for any changes in the same session.

**Changing a note or this guide**

- Ask for the change in a session. The AI edits the note's markup, or `CLAUDE.md`.

**Rendering**

Notes are built by `note.js` and printed to A4 by a headless Chromium-based browser (Brave here):

```
.claude/skills/memory-dump/render.sh notes/<name>.html [out-dir]   # → <name>.pdf, default: project root
```

PDFs are not kept in the project; the site makes them on demand. `archive/` keeps the PDFs from before
the HTML rebuild and the last guide PDF (2026-10-13), unchanged and no longer updated.

## 7. Rules for AI assistants

- Read this file before creating or changing anything in the chalk book.
- Use the `memory-dump` skill to make notes, and `chalk-pastel.css` for every colour.
- Match the existing notes' structure and look exactly; open one as a reference if unsure.
- **Read little first.** To find something, stop at the first step that answers it: the catalogue (`site/notes.js`)
  → hits with context, `grep -o -i -P '.{0,150}<word>.{0,150}' site/search-index.js` → one section,
  `sed -n '/^## Bugs/,/^## /p' notes/<name>.html` → the whole note only when the task needs all of it
  (redoing a recipe, editing a note, a privacy check, a new note in its style).
- Never edit, rename or delete an existing note or archived PDF unless the user asks.
- Change this guide only when the user asks, and keep `CLAUDE.md` and the guide's HTML in sync.
- Keep private data out *before* it is committed. A pushed commit can't be fully taken back: GitHub may still serve it
  by its hash after a force-push. If something slips through, tell the user; don't rewrite history without asking.
- **Git follows the person.** Whether to commit or push, and the commit-message style, come from the current user's
  own instructions (their global `CLAUDE.md` or memory), never from this file. If none are given, ask before any git action.
  Personal habits stay out of this file, so the repo serves whoever works on it next.
- **Git wording.** Use git's own terms exactly: *stage* (`git add`), *commit* (save a snapshot locally), *push* (send
  commits to GitHub), *pull*, *revert*, *reset*. If a request doesn't map clearly to one git action, don't guess: ask,
  offering 1–3 options, each with its command and one line on what it does.
- **Commit messages document the work:** a title, then a body saying what changed and why. The user's own style
  comes before any default.
