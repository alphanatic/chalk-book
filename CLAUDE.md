# Chalk Book — Project Guide

> A personal technical chalk book. After a session of problem-solving, building or
> learning with an AI, the work is distilled into one calm, skimmable note that
> can be revisited later for a fast refresher, on a small local site or as a PDF.

This file is the source of truth for how the chalk book works. It is written for any
future AI assistant or person picking up the project. A human-friendly copy lives in
`00-chalk-book-guide.pdf`.

---

## 1. Purpose

- **Capture** recent work while it is fresh — commands, configs, decisions, mistakes.
- **Revisit** it later and get the gist in under a minute.
- **Repeat** it cold, months later, without re-researching anything.
- **Trace** what was done, per project and date, so a future AI can skim the collection and
  recall which scenarios have been worked through.

### Two kinds of knowledge

Every note serves one or both of these readers:

| Kind | What it looks like | What the note must do |
|---|---|---|
| **Recurring** | Things used again and again (e.g. `systemctl`, `ssh` config, naming rules) | Be a fast *reference* — patterns, quick tables, the one flag you forget |
| **One-off** | Setup done once, or a rare fix (e.g. growing an EBS volume, a logrotate permission error) | Be a complete *recipe* — every step, in order, with every flag explained, so it can be redone from zero |

When in doubt, write for the forgetful future self: assume nothing is remembered.

### File naming

```
<project>-<NN>-<topic>.html
```

- `project` is the slug from the project list below, so the name says where the work happened.
- `NN` is two digits and counts up within each project, so `10` sorts after `09`.
- `topic` is 2–4 words naming the subject, not the outcome: `cron-logrotate`, not `fixed-my-logs`.
- Everything is lowercase kebab-case. One topic per file; a long session becomes several notes.
- The date lives inside the note (eyebrow chip) and in `site/notes.js`, not in the file name.
- `00-` is reserved for meta files about the chalk book itself.

### Projects

| Slug | Display name | What it is |
|---|---|---|
| `tinker-town` | Project Tinker Town | Self-paced AWS Linux sysadmin lab, a one-week crash course in 7 modules |
| `pokedex` | Pokédex | The Pokédex web project |
| `meta` | Chalk Book | Notes about the chalk book itself |

Add a row before using a new project, and the same project to `CHALK_PROJECTS` in `site/notes.js`.
A project can carry a roadmap of modules there; the site shows unfinished modules as planned.

### Note types

- **Walkthrough** — what was done in a session, start to finish. Most notes.
- **Reference** — a cross-cutting rulebook that other notes depend on
  (e.g. `tinker-town-05-naming-conventions`). Says so in its summary: *"a reference, not a walkthrough"*.

## 3. Anatomy of a note

Every note follows the same top-to-bottom shape, so the eye always knows where to look.

1. **Header band** (dark)
   - Eyebrow chip: `PROJECT TINKER TOWN · 03 · MODULE 1 · 2026-08-30` (project · number · module, if any · date)
   - Title, its words coloured in turn after the yellow chip: blue → pink → green → yellow
     (done by `notes/note.js`); every `&` is purple chalk (`--lav`), other symbols stay white
   - Subtitle: a short descriptive phrase
   - Summary: 1–2 sentences, past tense — what was built and why it matters to later notes
2. **Legend** — a row of colour chips for every block type used in that note
3. **What we covered** — checklist of ✓ outcomes, one line each, skimmable on its own
4. **Full command sequence** — the steps, grouped under short headings, each tagged
   `Local` or `Remote`
5. **Supporting sections** as needed — concepts, diagrams, field tables, quick-reference tables
6. **Bugs hit & fixed** — one card per real error: **Cause** → **Fix**
7. **Where things live** and **Best practices** (short cards) as needed
8. **Part of** line — the project, with links to related notes through the site
9. **Footer** (printed pages) — `Tinker Town 03 — Systemd Service · 1 / 3`

### Block types and colours

| Block | Palette colour | Used for |
|---|---|---|
| Local | `--sky` | Commands run on your own machine |
| Remote | `--lav` | Commands run on the server |
| Config file | `--butter` | File contents, with the path as the block title |
| Concept | `--peri` | The *why* behind something; command output |
| Gotcha | `--peach` | Traps that bit, or nearly did; bug cards |
| Best practice | `--mint` | The recommended way, and why |
| Paths | `--pink` | Important file and folder locations; tables; title accent |
| AWS Console | `--coral` | Steps done in a web console, not a shell |

Inline callouts use a bold label and a dot: **Gotcha ·**, **Concept ·**, **Key rule ·**, **Naming note ·**, **Updated rule ·**.

## 4. Writing style

- **Skim first.** Headings, checklists and tables carry the story; prose fills gaps only.
- **Short.** Sentences under ~20 words. No intro paragraphs, no filler.
- **Every command gets a comment** explaining what it does and what each flag means:
  `sudo mkdir -p /mnt/data   # -p: create parents, no error if it exists`
- **Config files stay clean.** Never put comments inside a config block (many formats
  break on inline comments). Annotations sit in a column beside the file, or in a field table below it.
- **Real by default, except access, location and private life.** Use the actual commands, paths and error messages
  from the session, with three exceptions:
  - **Access:** never write anything that grants access (keys, passwords, tokens, recovery codes), not even partly masked.
  - **Location:** anything that locates or identifies a host or account (public IPs, AWS account IDs, resource IDs,
    emails, internet hostnames) becomes a placeholder, `<what-it-is>` in lowercase kebab-case. Reuse an existing name
    where one fits: `<instance-ip>`, `<my-ip>`, `<vpc-id>`. Private ranges (`10.0.0.0/16`) and `0.0.0.0/0` are fine.
  - **Private life:** nothing about the user's life outside the work: real name or initials, home address, job search,
    health, other people. When in doubt, leave it out and ask.
  - **Admin users:** every personal admin account is written as `adm-kiwi`, in live and test environments alike,
    whatever its real name. The steps (creating it, logging in, sudo) stay exactly as they were done.
- **Keep the mistakes.** Errors and their fixes are often the most valuable part. Record them as Bug cards.
- **Respect history.** When a convention changes, update the reference note and mark old
  names as legacy (struck through, with a *Naming note*), rather than rewriting earlier notes.
- **Calm tone.** Plain, friendly and factual. No hype, no emoji.

## 5. Visual style

Soft, warm and easy on the eyes. Pastels only, no harsh borders, generous white space.

### Stylesheet rule

**`chalk-pastel.css` is the palette for every note, until the user says otherwise.**

- Every note links it (`<link rel="stylesheet" href="../chalk-pastel.css">` from `notes/`).
- Colours are used only through its variables, e.g. `var(--lav-bg)`. No hard-coded hex values
  in notes or in `note-layout.css`.
- Each colour comes in four parts: the chalk colour for chips and borders, `-bg` for box tints,
  `-ink` for coloured text, `-chip` for text on a chip. The comments in the file say what each is for.
- The file belongs to the user. Do not edit it unless asked.
- Changing the palette restyles every note at its next render. PDFs keep the old look until re-rendered.

### Layout

Structure and components live in `notes/note-layout.css`, shared by every note:

| Element | Look |
|---|---|
| Page | A4 portrait on `--paper` |
| Header band | `--asphalt`, title words in `--sky`, `--pink`, `--mint`, `--butter` in turn |
| Body font | Inter (bundled in `notes/fonts/`) |
| Code font | DejaVu Sans Mono |
| Code and config blocks | `-bg` tint with a coloured left bar |
| Callouts and bug cards | `-bg` tint, rounded corners, thin chalk border |
| Section headings | bold, with a small chalk dot to the left |

### The site

`index.html` is a small static site with no build step: open it straight from disk.

- A dark frame in the warm greys of Claude's dark mode, with each note shown as a pastel A4 sheet.
  The dark colours live in `site/site-theme.css`, kept apart so the note palette stays untouched.
- Left menu (`nav#nav-menu`): a search field on top, then notes grouped by project, a roadmap progress line and
  planned modules outlined. The menu button (three chalk sticks) in the top bar collapses it to a rail
  that shows only each note's number and colour bar; search becomes a tile with a diagonal chalk stick.
  File buttons are 20:3; the search field is an inverted file button.
- Search covers the full text of every note, plus its catalogue details. While typing, results replace
  the note list; each matching note shows once, with its number of hits, and opening it highlights
  every hit. It reads `site/search-index.js`; rebuild that after adding or changing a note:
  `node site/build-index.mjs`.
- Right panel: recently viewed notes, newest first, styled as the menu's mirror image and kept in the
  browser only. It is a rail of numbers and colour bars; hovering slides it open over the note in
  0.3 s, and moving away slides it straight back.
- The name is one shared element, `<chalk-wordmark>`: Chalk in blue, Book in yellow.
- The **main footer** (`main-footer`) is persistent on every page and links Home, **Backlog**,
  **Complete Tasks** and **Contact**, bold and coloured like note titles. Complete Tasks and Contact
  live in `site/pages/` and open in the viewer (`index.html#complete`, `#contact`). Add a page by
  creating it there and adding it to `PAGES` in `site/app.js` and to the footer in `index.html`.
- **Backlog** (`index.html#backlog`) and **Complete Tasks** (`#complete`) are private pages in
  `.prog/` (in `.gitignore`: they exist only on this machine, never on GitHub or a hosted copy):
  `.prog/index.html` and `.prog/complete.html`. Both show in the viewer with the
  nav menu and main footer; Recently viewed is hidden on the backlog. They cover Chalk Book itself
  only (the site, note format and workflow); work inside a menu project belongs in that project's
  roadmap in `site/notes.js`.
- **Complete Tasks** keeps finished items in the backlog's look: an Overview table whose rows link to
  the cards below, then the cards, green-barred with the title crossed off. The first items keep
  their old numbers (`C12`, `C13`, `C16`).
- **Moving a finished item** happens only when the user asks; there is no button. Move the item's
  whole `<article>` from `.prog/index.html` to the top of the matching section in
  `.prog/complete.html` (add a section if needed), unchanged except: `data-status="done"`, the
  status chip becomes `<span class="chip done">Done</span>`, and a `<span class="date">YYYY-MM-DD</span>`
  is added to its header. Keep its number and `id`, so links keep working. Move its overview row too,
  with the date in the Done column, and remove both from the backlog. Never invent details for an item.
- The earlier in-site backlog (numbered C-items, status bars, criticality ranks, legend) is recorded in
  `archive/backlog-workflow/`, which is private and never committed.
- **Export** (top right) opens a small dark menu. Its one option for now, **Save as PDF**, opens the
  browser's print dialog for the open note; Brave or Chrome give the same result as `render.sh`.
  More options (e.g. mail) can be added as items in that menu.
- The menu always starts as a rail; the menu button opens it beside the note and closes it again.
- The name in the top bar sits on the left beside the menu button, as plain text (not a link). On
  smaller windows the top bar drops the name first, then the note title; the menu button and Export stay.

## 6. How notes are made and changed

The notes are **read-only by design**: nobody edits a note in a viewer. Every change
goes through an AI session.

**Adding a note: the memory-dump skill**

1. Work on something, in any project folder.
2. While it is fresh, say **"memory-dump"**, "chalk that up" or similar. A personal pointer skill in
   `~/.claude/skills/memory-dump/` makes this work in every folder and leads back to this project.
   An AI may also offer a dump when the topic changes or about an hour of content has built up.
3. The skill plans the note(s), copies `template.html` into `notes/`, fills it in following this
   guide, adds it to `site/notes.js`, rebuilds the search index, checks every page, then commits and offers to push.
4. Check the note on the site; ask for any changes in the same session.

**Changing a note or this guide**

- Ask for the change in a session. The AI edits the HTML source, or `CLAUDE.md`.
- After `CLAUDE.md` changes, `notes/00-chalk-book-guide.html` and `00-chalk-book-guide.pdf` must be
  updated so the three stay in sync.

**Rendering**

Notes are HTML + CSS printed to A4 by a headless Chromium-based browser (Brave here):

```
.claude/skills/memory-dump/render.sh notes/<name>.html [out-dir]   # → <name>.pdf, default: project root
```

Note PDFs are not kept in the project; the site makes them on demand. Only the guide PDF lives
in the root. The original PDFs from before the HTML rebuild are kept in `archive/`.

## 7. Rules for AI assistants

- Read this file before creating or changing anything in the chalk book.
- Use the `memory-dump` skill to make notes, and `chalk-pastel.css` for every colour.
- Match the existing notes' structure and look exactly; open one as a reference if unsure.
- Never edit, rename or delete an existing note or archived PDF unless the user asks.
- Keep `CLAUDE.md`, the guide's HTML and `00-chalk-book-guide.pdf` in sync.
- Change this guide only when the user asks. It is meant to stay stable.
- Keep private data out *before* it is committed. A pushed commit can't be fully taken back: GitHub may still serve it
  by its hash after a force-push. If something slips through, tell the user; don't rewrite history without asking.
- Commit locally as needed, but push only when the user asks for it.
